# Could Zona Dron be multilingual?

Short answer: **the interface, yes; the whole app, no.** A language switch in
Settings is perfectly doable, and this note is the survey of what it would take
and where the honest limits are.

Nothing here is implemented. The app ships in Spanish only.

## Where the app stands today

- No i18n library, no message catalogues, no `expo-localization`. Every visible
  string is a Spanish literal inside the component or module that shows it.
- Roughly **400–450 user-visible literals** across `app/` and `src/`, heavily
  concentrated in a few files:

  | File | Literals | What they are |
  |---|---:|---|
  | `src/logic/rules.ts` | ~60 | Regulation summaries, one paragraph each |
  | `src/logic/labels.ts` | ~38 | ED-318 code → human label |
  | `src/logic/verdict.ts` | ~35 | The verdict sentences, composed at runtime |
  | `src/logic/drone.ts` | ~22 | Drone class descriptions |
  | `src/logic/request.ts` | ~16 | The authorization e-mail template |
  | Everything else | ~230 | Screen titles, buttons, empty states, errors |

- **13 call sites** format dates and times with a hardcoded `'es-ES'` locale
  (`src/logic/sun.ts`, `src/logic/share.ts`, `src/components/WeatherCard.tsx`,
  `src/state/HistoryContext.tsx`, `app/diario.tsx`, `app/luz.tsx`, …).
- `src/api/geocode.ts` asks Nominatim for Spanish results with an
  `accept-language: es` header, in two places.
- `src/map/mapHtml.ts` builds the Leaflet page as a string, so it carries its
  own handful of labels inside the WebView.
- The iOS location-permission text lives in `app.json` (`infoPlist`), and the
  Android one in the `expo-location` plugin config. Those are native strings:
  translating them means shipping `InfoPlist.strings` per language and declaring
  `CFBundleLocalizations`, not just a JavaScript dictionary.

## What cannot be translated

This is the part that decides how far a language setting can go.

- **ENAIRE zone data.** Names, official free text, restriction conditions and
  contact details arrive from the service in Spanish. There is no English feed.
  Machine-translating a legal restriction to then act on it is exactly the wrong
  move for an app whose whole point is not being wrong about restrictions.
- **NOTAMs.** Raw aeronautical text, ICAO abbreviations, mixed Spanish and
  English. Not ours to rewrite.
- **Protected natural areas.** Official names of parks and reserves, in Spanish
  and in the co-official languages of each region.
- **The authorization request** (`src/logic/request.ts`). It is an e-mail sent
  to Spanish authorities and zone managers. It must stay in Spanish whatever the
  interface language is — this is a case where the correct behaviour is *not*
  to translate.

So a translated app would always be bilingual on screen: English chrome around
Spanish official text. That is normal for aviation tools, and worth stating in
the UI rather than hiding.

## What a language setting would involve

1. **A tiny `src/i18n/`** — `t('key', params)` over a per-language dictionary
   object. No heavyweight dependency needed; the app has no plural-heavy or
   gendered copy that would justify `i18next`, though the verdict sentences do
   need plurals (`1 zona` / `4 zonas`), so the `t()` helper should take a count.
2. **A `language` field in `SettingsContext`** — `'sistema' | 'es' | 'en'`,
   persisted alongside the existing settings, defaulting to the device locale
   via `expo-localization`. The settings screen already has the right shape of
   control for it (see how `appearance` is done).
3. **One locale string threaded through the formatters** instead of the 13
   hardcoded `'es-ES'`, plus the two `accept-language` headers in `geocode.ts`
   so place names come back in the chosen language.
4. **Extraction, file by file.** The concentration above is good news: five
   files hold about a third of the strings.
5. **Native permission strings**, if the system prompts should match.
6. **A note in the UI** explaining that official zone text stays in Spanish.

Realistically a couple of days of mechanical work for a first English
translation, most of it in step 4, plus the ongoing cost that every new string
now has to be added in two places.

## The recommendation

Worth doing if the app is meant for visitors flying in Spain — which is a real
audience, and the one that most needs a plain answer about a regulation they
have not read. Not worth doing halfway: a half-translated interface is worse
than a Spanish one, because it makes the untranslated official text look like an
oversight instead of a deliberate choice.
